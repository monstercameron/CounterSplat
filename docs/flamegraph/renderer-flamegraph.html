Why the renderer is slow: flame graphs

Nelson Ghost Town (5.1 M splats, streamed) in the Claude built-in browser pane on the integrated NVIDIA GPU, captured with the engine's own profiler (?stack_profile=1: 180 frames, GPU timestamp queries on every third frame, JS Self-Profiling stacks). Width is time; click a block to zoom, click the root to reset.

1. GPU frame, camera moving

draw / sortpost / UI

Mean of 41 timed frames while strafing. The GPU, not the CPU, sets the frame time: the sort re-runs every frame the camera moves, and the splat draw is the rest.

2. GPU frame, camera still

Mean of 45 timed frames, no input. The sort is skipped, but the draw alone is still about 12 ms (range 8.8 to 33.8 ms; the long frames are chunk uploads landing on the same GPU).

Mean of 42 detailed frames: about 3 ms of the page thread per frame, all of it hidden behind the GPU. These are timed spans, not samples, so they are exact.

91 samples at the browser's 16 ms minimum interval: 59 were idle (the thread was waiting on the GPU or the next frame) and 32 were busy; 26 of the busy stacks are drawn here (the rest were single, very long Lua stacks left out). 5. After the segment work: GPU frame, camera moving

Same level, same strafing input, 60 timed frames. Read the A/B column below rather than this absolute total: between sessions the GPU's clock state moved even untouched code by up to 2x (the unchanged static draw measured 12.4 ms in one session and 6.0 ms in another).

What the graphs say

  • The frame is GPU-bound. The page thread needs about 3 ms of a 8 to 14 ms frame. Optimising Lua, ECS or the Rust frame code cannot make it faster.
  • Camera still: about 12 ms of GPU time is the splat draw (scene_draw). The post-process pass is 0.28 ms and the UI is free.
  • Camera moving: add about 4.8 ms for the depth sort (splat_prepare) on top of about 10.4 ms of draw: roughly 15.5 ms, or 65 fps. That is the number a player feels.
  • Why the draw is slow: earlier native measurements (splat_bench) showed it is vertex-bound: four vertices per splat for every splat in the visible prefix, so cost follows splat count, not pixel count. It is about 9 ms per million drawn splats on this shared-memory GPU.
  • Limits of this capture: GPU timers cover four zones, so the inside of scene_draw (sky, splats, overlays) is not split further; the browser caps JS stack sampling at 16 ms; the headless pane is one GPU and one display, so absolute numbers are for this machine.
